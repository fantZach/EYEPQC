# 三端架构与目录契约

2026-10-12 用户确认：保留开发板 USB Slave，利用 PC 联网，移动端解密视频。
平台条件：PC 为 Windows，移动端为 Android。
本文定义三端架构；Windows 密文桥与 Android 应用源码已有，软件互操作通过，实际板卡/手机链路待验。

2026-10-14 更新：公网中转新增独立 `server/`，形成四个维护子项目。
当前公网实现采用PC主动OpenSSH反向TCP隧道，云端公开端口转至PC回环WSS；
TLS和账号校验仍在PC，Android/Board业务协议不变。此决定不表示公网已验收，
统一部署/限制见 [公网中转契约](cloud_relay_plan.md)。以下旧接口/历史阶段不迁移为新门禁通过。

## 部署与职责

```text
局域网：开发板 ⇄ USB ⇄ PC（接入服务） ⇄ Wi-Fi/局域网 ⇄ 移动端
公网：  开发板 ⇄ USB ⇄ PC ⇄ 公网中转服务 ⇄ 移动端

视频：板端采集、加密 → PC → [中转] → 移动端验 Tag、解密、显示
控制：移动端 ⇄ [中转] ⇄ PC ⇄ 板端（HELLO / KEM / Finished / START / STOP / REKEY）
```

| 子项目 | 拥有的代码 | 目标职责 |
|---|---|---|
| `board/` | RTL、PS 固件、第三方密码核、XDC、`prj/` 构建/调试工具 | 摄像头、DMA、ML-KEM Decaps、AES-GCM 加密与 USB 从机 |
| `pc/` | Windows Python 主机工具；后续 USB/网络桥和中转服务 | 连接板卡、透明转发双向记录、连接授权及有界队列 |
| `mobile/` | 后续 Android 应用 | 公钥 pin、ML-KEM Encaps、Finished、认证解密与视频显示 |
| `server/` | 受限 OpenSSH 配置、Linux 服务及部署校验 | 认证PC隧道公钥、透明TCP中转，不终止业务TLS或解密视频 |

`doc/`、`sim/`、`data/kat/`、`report/` 为共享契约与证据。根目录脚本负责跨项目编排。
公网服务由独立server项目维护，PC维护对应主动隧道入口。第一步使用同一局域网，不需要租服务器；公网实现按实际接入条件部署。
板端继续裸机运行，不因网络中转引入 Linux、USB 网卡或板端 TCP/IP 改造。
Android 使用原生 Java Activity、OkHttp 4.12.0、Bouncy Castle 1.81 lightweight ML-KEM；最低系统 API 26，编译/目标 API 35。
Windows PC 与 Android 也可通过组网 VPN 访问 PC 接入服务，作为局域网之外的可选路径。
VPN 供应商尚未选定，校园网连通性、直连/中继和视频吞吐须实测，不能预先标为通过。

## 协议与传输

保持 [EYEPQC v1](protocol.md) 字节协议、ML-KEM-512、AES-128-GCM、1400 字节视频分片和 40 字节 AAD。
外层记录为 `channel:u8 || record_length:u16_be || record`；控制记录最多 1036 字节，视频最多 1456 字节，
包含 3 字节外层头后单条最多 1459 字节。转发器先检查长度与方向，再路由原始字节。
外层路由字段不是身份或认证依据，接收端仍须验证内层控制 MAC / 视频 Tag。

已实现的最小网络适配为二进制 WebSocket：每个网络消息承载一条完整 USB 记录，
USB 侧继续处理拆包、粘包和超时半包。公网使用 WSS；网络加密不替代应用层 AES-GCM。
PC 和移动端均可主动连接远程中转，服务器按经过授权的设备/观看会话配对，
不得仅凭可猜的房间号开放视频。局域网模式已加入 Bearer 令牌接入授权；远程中转配对与部署仍待实现。

MVP 只允许一块板对应一个活动观看端。PC 同时只能由纯转发器或原有解密演示独占 USB，
第二个观看者须明确拒绝，不能让两个控制流交叉进入板端会话。多用户不在本阶段范围。

队列固定最多64条/单条1459字节。PC读取公开视频头，在帧首按packet_count判断整帧能否容纳；
空间不足或缺首片则舍弃该帧全部分片，继续读取USB，转发的AAD/Tag/密文字节不改、不解密。
控制消息不丢弃，预留本次读取批次中的控制空间；控制溢出、非法记录或传输超时仍关闭会话。
每发送至少64KiB应用记录，用标准WebSocket Ping/Pong确认远端已读取此前网络字节，
限制SSH/TCP链路中的积压；Ping发送和Pong等待合用原5秒上限，不是业务GCM确认。
大于整个64记录预算的单帧也被舍弃，扩大分辨率前须改成独立帧/字节预算。
正常DTR/USB epoch断连清理旧业务密钥并等待全新握手；真实致命错误仍清除身份且保持FAULT，不能伪恢复。
不拼接新旧会话，不任意截断控制记录。低带宽/非正常退出的实板回归见 [修复记录](../report/handshake_recovery_20261015.md)。
断连后的 DTR/固件恢复路径必须经过实际板测，不能将历史 G7 部分结果视为新中转路径已通过。

## 密钥边界

移动端预置信任的板卡公钥 pin，生成封装随机数，与板卡通过双向 Finished 确认会话。
最终只有板端和移动端使用业务 video/control 密钥。PC/远程服务不解密、不改写 AAD/Tag/密文，
不记录秘密或 JPEG 明文，不将测试私钥打包给手机；公开 KAT 向量与实际 provisioning 材料必须区分。

现有 v1 完成接收端对板端的公钥固定验证，并未实现观看者的板端身份认证。
因此公网服务还需设备/用户接入授权；Finished 的密钥确认不能替代观看权限管理。
当前开发测试私钥与随机 seed 经 PC/JTAG 装载，该 PC 可以接触板端长期私钥，
迁移到手机握手后也不能声称对恶意 provisioning PC 保密。真实熵/provider、密钥生命周期及启动/调试保护仍是独立生产门禁。

## 迁移与验收

目录迁移之后新增 `pc/src/host/relay.py` 密文桥和 Android 接收端；`/stream` 采用 Bearer token，
每个二进制消息是一条完整 USB 记录。桥默认只监听回环，只有显式选择接口才开放网络；WSS 需有效证书。
明文 WS 会暴露接入令牌，仅在受信任的局域网或受保护 VPN 中使用；视频仍由应用层 AES-GCM 保护。
原 PC 解密演示保留，用于与手机移植结果交叉验证。旧报告保留原路径与哈希，
旧生成工程/manifest 不改写；重建时使用新目录及新的输出位置，严禁绕过来源一致性检查。

后续按 `M16 PC 转发 → M17 手机接收 → M18 可选公网部署 → M19 端到端验收` 推进，详见 [steps](steps.md)。
离线模拟不能替代手机/板卡实测；目标 45 fps 需在手机实际认证解码显示处重新测量，并同时记录网络码率与延迟。
原有 G0～G7 的未完成项目继续保留，不由新增网络验证抵消。
