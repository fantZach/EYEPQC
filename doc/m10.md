# M10：KDF、会话与密钥管理

## 实现

板卡 A9 的 `src/ps/src/session.c` 与主机 `src/host/handshake.py` 按
[协议](protocol.md) 派生 56 字节：AES-128 视频密钥、HMAC-SHA256 控制密钥、
32 位 Nonce 前缀和 32 位会话 ID。transcript 纳入固定公钥哈希及三条完整握手消息。
板卡 SHA-256 使用 [Intel TinyCrypt](https://github.com/intel/tinycrypt)
提交 `cf24c907a61c01bc2c4e1ee0ae24457c27a840a2` 的未修改源码，
[BSD 三条款许可证](../src/third_party/tinycrypt/LICENSE) 随代码保存；HMAC/HKDF
由本项目的小型包装实现，主机使用 Python 标准库。RFC 5869 的 HKDF、RFC 4231 的
HMAC 向量和 C/Python 逐字节比对均在 `sim/tb/test_m10.py` 中执行。

状态为 IDLE、HANDSHAKE、CONFIRM、STREAMING、REKEY、ERROR。主机先验证板端
Finished，再发送自身 Finished 和带序号/MAC 的 START；板端全部验证成功才允许
分配视频序号，并把派生视频密钥和第一个 Nonce 装入 G3 的 PL AES-GCM 寄存器。
每次分配 64 位序号即消耗一次，不回收；临近回绕时进入 REKEY。已认证 REKEY、
错误和清理均清除 PS 会话密钥并向 M08 寄存器写入 abort/zeroize；主机只在
GCM Tag 验证成功后调用重放窗口。用户主动重协商通过认证 REKEY，断连/错误
恢复必须重新封装并使用双方新的随机数，旧 transcript、Finished 和旧会话 ID
均拒绝。v1 不提供主机身份认证。

## 复现

```powershell
python sim/tb/test_m10.py
$env:EYEPQC_M10_VITIS = 'C:/Users/23976/Desktop/WorkingOn/EYEPQC/build/vitis/m10_fresh'
& 'D:/AmdDesignTools/2026.1/Vitis/bin/vitis.bat' -s prj/build_m10.py
python src/host/m10_board.py --workspace build/vitis/m10_fresh
```

板测沿用 M09 的 `board/output/m09/` 静态密钥；没有文件时先运行
`python src/host/m09.py build` 和 `python src/host/m09.py keygen`。需连接 JTAG、
运行 `hw_server`，不需要以太网或串口。Vitis 构建前用 `EYEPQC_M10_XSA`
选用含 G3 AES-GCM IP 的 XSA，默认当前 G3 快速模式 XSA。构建记录源码、XSA、
bitstream、ELF 哈希及 ELF 自有 DDR 地址；板测前全部核对。板端调试邮箱仅用于
离线验证，会回传派生材料以便逐字节比对，不能用于生产。私钥和调试文件留在
被 Git 忽略的 `board/output/`；Python 不可变字节对象不能保证内存擦除，
TinyCrypt/此离线流程也不是完整的抗侧信道产品安全方案。JTAG 测试由主机生成
模拟的 HELLO_ACK 随机数；真实握手必须由板端安全随机源生成，留待 M11/G6。

## 2026-09-29 实测

- PC：SHA-256、HMAC 标准向量；C/主机 KDF、Finished、命令、Nonce 逐字节相符；
  重放、近回绕重协商和清零路径通过。
- CF7020B A9 + G3 bitstream：JTAG 完成两次新密钥会话、一次认证重协商、
  故意重放旧 Finished 后拒绝并清零、错误后新会话恢复。主机旧 session_id
  的数据包被拒绝；三次会话的 Key/Nonce 组合不同。
- 本测不传真实 USB 视频；M11/M12/G6 再接入 USB 收发与完整分片认证。

板端报告与每条 JTAG 日志位于忽略的 `board/output/m10/`。
