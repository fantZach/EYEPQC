# 会话密钥与清零边界审阅

更新：2026-10-08。审阅对象为当前 G6/M10 开发态实现；此项是源码审阅和离线回归，不是设备安全认证或全内存清零测试。

## 代码当前能证明的范围

| 区域 | 代码行为与已有证据 | 不能由此证明 |
|---|---|---|
| PS 会话对象 | `eye_session_error/rekey` 用 volatile 写擦除 transcript hash、视频密钥、控制密钥，并将 Nonce 前缀、session ID、收发序号和 replay 状态归零。M10 离线/旧 JTAG 测试覆盖重协商、重放拒绝和对象内零化标志。 | 不能代表整个 A9 栈、寄存器、缓存、DDR 和调试路径已无副本；单个 `session` 结构体状态不等于全域零化。 |
| PS 长期私钥/种子 | G6 清除 JTAG mailbox `g6_sk_load`/`g6_seed_load` 后拷贝到静态 `private_key`/`random_seed`。初始化失败会 wipe 这两个私有数组；正常断线、STOP、REKEY 和会话错误仅清会话对象/PL，长期私钥和运行种子仍在 PS RAM，这是当前握手继续运行所需状态。 | 不能证明掉电、复位、异常处理或 JTAG 调试下不可读；也未有启动/结束后逐地址 RAM 读回清零的验收。 |
| 板端随机数 | `board_random()` 计算 HMAC-SHA256(random_seed, HELLO host_random || counter)。本轮 seed 来自主机 CSPRNG 并经 JTAG 注入；板端没有被代码调用的 TRNG、熵健康测试或经审计 DRBG。 | 不构成设备可信熵源；种子被读出或重启时复用会破坏前向/重启安全属性。 |
| PL AES-GCM key/nonce | 每帧加密前装载会话 Key，使用硬件 nonce/序号参数；发送帧后调用 `g3_usb_zeroize()`，STOP/REKEY、连接代数变化和 fail-closed 也调用该命令。M10/G3 邮箱和 RTL 零化路径有离线/既有板测证据。 | 不能证明所有时钟/复位/中途断电次序下寄存器全清，也不能证明总线/综合工具残留或 side-channel 安全；当前批次未读回 PL 全部 key/nonce 状态。 |
| 摄像头 DMA/DDR | 摄像头 JPEG 位于 `g3_frame`/DMA DDR 缓冲；现有采集与 USB flush 管理缓冲所有权/队列，部分结果邮箱及 GCM 临时块有清理路径。 | G6 正常断线/STOP 路径没有对整块 DDR 明文帧执行 wipe；DMA 停止、缓存写回/失效、DDR 全面清零没有本轮逐地址证明。不能把密钥零化外推为明文清零。 |
| USB 端点/队列 | bus-reset/DTR 路径撤销 configured/DTR，清软件接收环；端点禁用、有界 flush、清 descriptor/QH 状态并重建队列。G7 仿真/helper 检查了分支，实际 USB 物理拔插曾单次通过，本轮主机进程异常退出重复 20 次。 | 无法证明主机 USB 控制器内部、所有端点缓存、线缆/设备外部副本被安全擦除；也没有对每个 DMA descriptor 做板端读回审计。 |
| 主机 Python 对象 | `HostSession.close()` 将 `bytearray` 视频/控制 Key 覆盖为零；G6 最终清理 `previous_key` 和 ML-KEM 私钥 bytearray。批次只持久化视频 Key 的 SHA-256 指纹，不写 Key/私钥/seed。 | Python 不可变 `bytes`、扩展模块/密码库副本、解释器临时对象、堆分配器与崩溃转储不保证可清除；不能声明进程内秘密已全面擦净。 |

## 可执行的生产化路线

1. **确认板端熵源可行性**：先核对当前 CF7020B/领航者原理图、器件配置和实际连线，列出可访问的熵源候选与数据通路。当前仓库未记录可用板载 TRNG/噪声源，不凭器件系列推断能力。若没有可验证的板载源，评估可审计的外部熵器件及布线改版；未满足熵源前，G6 保持开发态。
2. **定义随机服务**：把熵采集、启动熵不足处理、健康测试、调理/DRBG、重播种与计数器状态独立成模块；健康检查失败时禁止 HELLO_ACK/ML-KEM 密钥操作。固定源版本、标准向量、故障注入和熵评估证据。
3. **设备身份密钥**：停止生产路径 JTAG 私钥注入。先选定具体可恢复 provision/安全存储方案，明确量产注入、读取权限、密钥轮换、RMA/返修和擦除行为；随后测试冷启动、复位、断连、认证失败及升级异常。
4. **划定清零域并观测**：建立机密数据清单和生存期，覆盖 PS 长期私钥/临时共享秘密/会话密钥、stack/heap、缓存、PL AES 状态、DDR 明文帧、USB descriptor/环形缓冲和主机对象。对每个路径定义写零实现、内存屏障/cache 维护、可读回见证及失败安全条件；用 JTAG 读回只能作为开发验证，不能等价为关闭 JTAG 的产品安全证明。
5. **再做安全门禁**：复位/掉电边界、错误路径和断线循环需硬件重复测试；结合威胁模型评估 JTAG 生命周期、调试口锁定、secure boot、物理攻击/侧信道和故障注入。只有完成具体平台证据后，才能重新表述设备密钥与清零级别。

本次未发现应在当前正常开发路径直接改写的单点密码实现缺陷；主要缺口是有意采用的 JTAG 开发注入、未验证的板端熵源以及尚未覆盖的内存清零域。不得将 20 次主机异常退出恢复或 M10 对象级零化当作生产安全验收。
