# G6 SD cold-start gap audit (2026-10-15)

This first pass is read-only analysis of the board project. No SD card, board,
JTAG, UART, USB port, live service or real private-key/seed file was accessed.
No G6 cold-start success or production-security acceptance is claimed.

## Existing capability

- G0 FSBL/bitstream/self-test already boots from SD. The 2026-10-13 record covers
  the replacement MBR/FAT32 card, independent reader-reinsert hash verification,
  the user's ten-minute exception and a scoped physical PS reset window. That
  image is not G6 video firmware.
- `board/prj/build_software.py --boot-images` already generates an XSA-matched
  FSBL, checks `ps7_init.c/.h` against the XSA, and builds FSBL + bitstream + app
  with Bootgen. Bootgen's partition readback and image hashes are retained.
  `generate_bsp.tcl` adds `xilffs 5.6` for this flow; FSBL uses the SD/FatFs path.
  A second packaging wrapper is not needed.
- The common ARM linker already drops the orphan build-id section that caused
  the original zero-load-address handoff failure. New builds must retain the
  existing ARM startup/ELF/manifest verification, not reuse the failed image.

## Actual blocker

The development `g6_usb.c::main` initializes camera and USB, then waits for
`g6_ready == PROVISION_MAGIC`. Its 1632-byte ML-KEM identity secret and fresh
32-byte seed currently arrive through JTAG-owned DDR mailboxes. Therefore a
G6 BOOT.BIN alone can start the application but cannot provide authenticated
video after a cold start. The existing `prepare_mobile.py` is not an SD loader.

The production variant is deliberately separate. Its provider contract requires
protected identity decapsulation and evaluated entropy with source health
checks; it does not export the identity secret. The repository has no reviewed
implementation for the actual board. A PC seed, static SD seed, timer value or
XADC sample cannot silently satisfy this contract. Neither a provider interface
nor HMAC_DRBG establishes a physical entropy source or authenticated boot.

## Smallest choices requiring confirmation

1. Development demonstration without JTAG: SD stores only boot firmware; a
   trusted local PC keeps a dedicated test identity and automatically provides
   that identity plus a fresh OS-generated seed through local USB after each
   cold start. This needs an explicitly separate development-only USB bootstrap
   and a PC-side pre-session step. Existing authenticated video protocol must
   remain unchanged. It avoids placing a real identity secret on SD, but the PC
   remains trusted and knows development randomness; it is not production
   security, forward secrecy or autonomous operation without the PC.
2. Autonomous production-style startup: supply an actual reviewed key service,
   evaluated external/PL entropy source and trustworthy boot chain. Those are
   missing prerequisites, not a software flag to enable.

An alternative plain-SD test identity would additionally need explicit approval
of physical-readable private-key storage, and would still require a source of
fresh startup randomness. Merely copying identity + a fixed seed onto SD is not
an acceptable implementation.

The statements above describe the initial read-only audit, before the user's
approval. The following implementation supersedes its pending-choice status.

## Approved development implementation (2026-10-16 verification)

The user approved SD firmware plus a trusted-PC USB test-identity/fresh-seed
bootstrap. `doc/g6_sd_usb_bootstrap.md` freezes the EYBS v1 wire contract and its
development-only security boundary. No production provider was substituted.

- `build_software.py --g6-dev-usb-bootstrap` selects a distinct cleanup-enabled
  G6 profile, rejects mixed JTAG/production flags, requires SD0 MIO40..45 when
  building boot images, and verifies the resulting ELF has `usb_bootstrap` but
  no `g6_sk_load`, `g6_seed_load`, `g6_ready` or production initialization state.
- `g6_dev_bootstrap.h` implements WAIT/RECV/READY/terminal FAULT, strict header,
  lengths, consecutive offsets, one-shot load and an absolute ten-second
  receiving deadline. It wipes the material buffer on activation or fault.
- `g6_usb.c` validates the actual ML-KEM-512 secret key and public-key SHA256 pin
  before committing the identity and seed. The activation commit rechecks the
  USB epoch/readiness/deadline with interrupts held; any failure remains closed.
  Normal session disconnect/STOP/REKEY retains only this boot's identity, as
  before. A fault cannot be recovered by sending more bootstrap material.
- `usb_probe.c` clears CPU-owned receive-ring/record/completed OUT copies and
  detects interrupted partial DATA. It does not wipe a DMA-owned buffer early.
- UART markers are `G6_DEV_USB_WAIT boot_mode=0x..` and
  `G6_DEV_USB_READY boot_mode=0x..`; their boot-mode source is the read-only
  Zynq BOOT_MODE register. They contain no identity key or random seed.
- Existing schema2/suite2/type10/type11 and business controls remain unchanged.
  The PC side separately restricts EYBS to local explicit initialization, not
  authenticated network control forwarding.

No real key/seed was read by this board verification. The image contains no
identity secret or fixed seed. The trusted PC will know development identity
and startup randomness and transmits them over local USB; this is not a
production-security or PC-independent deployment claim.

## Deployment gate / remaining evidence

The frozen artifact has no identified offline blocker to writing the approved
SD card. The coordinator must recheck the exact current drive/disk identity and
old BOOT hash, exclusively create `BOOT.NEW`, flush and verify its readback,
rename the old BOOT to a non-overwriting card-root backup, and then promote the
new file. On failure, preserve new evidence and restore only those exact paths;
do not format, write a raw disk, recursively delete or overwrite unrelated data.

This board reviewer did not access F:, SD, JTAG, COM, USB or a live service.
Writing/readback is not reader-reinsert persistence. Neither is an offline
BOOT/ELF check a physical cold-start or authenticated-video pass. Those require
separate actual operator/UART/USB evidence, without JTAG, followed by the
existing suite2 handshake and video checks. Cold restart/new-seed, normal
reconnect and malformed/partial-load fault cases must be recorded separately.
