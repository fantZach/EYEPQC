# G7 主机接收进程退出重复验收

更新：2026-10-08。此批次只覆盖主机接收进程被强制终止后的新握手和视频恢复，不覆盖 USB 物理拔插、摄像头故障、DMA 超时或完整 G7 门禁。

## 结果

批次目录：[逐次记录](g7_runs/g7_batch_receiver_exit_20261008_191521_103_eae05d0e/)；机器汇总为 `batch_summary.json`。20 个 trial 均通过。每个 trial 都先收到当前会话至少 2 帧经 GCM 验证、JPEG 解码的图像，再强制结束本批次自有接收进程，之后不重载 JTAG，重新握手并收到至少 93 帧认证视频。恢复速率为 47.455～47.670 fps；40 个旧/新 session ID 与 40 个会话密钥 SHA-256 指纹均互不重复。未记录密钥本身。

全部恢复结果指向相同 manifest、ELF 和 XSA；20 次试验 `jtag_reload=false`。恢复端的主机认证/重放/乱序/分片/JPEG失败与丢帧计数均为零。板端 capture/DMA/USB 计数未从固件读回，仍是 `null`，所以这里只说明主机恢复与认证结果，不宣称板端错误计数为零。

每一轮的独立 JSON 同时引用故障前运行的 `result.json`、恢复后的 `result.json`、会话 ID、密钥指纹、帧数、错误统计和保存图片。离线交叉核验确认 20/20 trial 各只有一个通过记录，旧/新会话 ID 与指纹对应各自原始结果，build 身份一致。80 张引用图片中 79 张可再次解码为 640×480 JPEG；trial 10 的故障前 `last.jpg` 在旧版直接写文件时遭进程终止，文件不完整。该图片被排除为有效证据；故障前首帧有效，逐帧认证/解码计数和 READY 阶段记录有效，20 次判定不依赖该损坏快照。恢复后保存图片均可解码。

批次目录保留两次由调度器造成的失败尝试（trial 5 try01/try02），其当时已完成真实会话和帧传输，但旧调度器从 captures 目录按创建时间关联结果时发生竞态，无法把 session ID 关联到当前 partial JSON，因此安全停止且未记为通过。修复后由接收器在启动时打印精确 `G6_RUN_RESULT` 路径；同一批次断点续跑，try03 通过。这些是脚本证据关联失败，不是 G6/USB恢复失败。另有一个更早的单次探测批次 `g7_batch_receiver_exit_20261008_191255_508_2bfe09d9` 保留 1 个失败、0 个通过，原因相同。

## 运行与验证

`run_g7_batch.ps1` 先核对 G6 源构建清单、CDC 枚举、基线和活动 receiver；每个 trial 都用 `--no-jtag`。有边界超时，失败即停。`-ResumeDirectory` 只累计同构建、有效且唯一的通过 trial；新尝试使用新的 `tryNN` 文件，不覆盖失败证据。

已通过 `-DryRun`、20 次软件 mock、注入调度失败立即停止，以及“少于 2 帧不得终止/计通过”的 mock 门禁。`sim/tb/test_g6.py` 9/9 通过。逐帧快照和 JSON 后续改为同目录临时文件加原子替换；离线故障检查确认替换失败时原完整快照仍保留。修复后的原子写只在本轮离线验证，未重新占用板卡。

本批次不改变既有 2 小时长测例外。G7 尚缺 USB 物理拔插原计划余下 19 次、摄像头故障和真实 DMA 超时；软件 `g6_fault_inject` 只触发 capture-status 错误分支，不能用作 DMA 超时验收。G0 LED/复位、断电冷启动与 SD 独立启动仍需现场完成。

## 调度器审阅

本轮离线审阅为 `run_g7_batch.ps1` 和新增 `run_g7_usb_unplug.ps1` 加入断点续跑检查：每个通过记录的 JSON trial/try 必须匹配文件名；已通过 trial 必须是从 1 开始的连续集合且数量与汇总一致；重复编号、跨构建记录和不完整证据拒绝续跑。ReceiverExit 的异常处理与退出清理现在同时跟踪并终止本批次自有 recovery 进程。此项仅改变调度器校验/清理，不改写上述历史 20 次实测记录。离线验证包含 ReceiverExit DryRun/20 次 mock/失败停止/少帧拒绝，以及 USB runner 的稳定 PnP 状态 mock、歧义与超时拒绝、清理路径、失败后断点续跑；未连接或轮询板卡。
